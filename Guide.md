# rcx Server: Host Guide

This guide is for the person **running the server**. It covers configuration, starting the server, generating passwords for participants, and sending them out.

If you are only *using* the server, read `UserInstructions.md` instead.

---

## 1. How it works

- The server hosts a fixed set of questions (12 right now, defined in `questions.rs`).
- Participants open `index.html` in a browser, enter the server address and their personal **password**, load the questions, and test inputs against the hidden solutions.
- Each password is a signed token (JWT) tied to one email address. It expires **3 hours after it was generated**.
- Requests are rate limited **per email address**, so one person cannot flood the server.

### Endpoints

| Method | Path | Purpose |
|--------|------|---------|
| GET | `/load` | Returns the list of question statements |
| POST | `/ask/{index}` | Runs question `index` (0-based) on the input in the request body |

Both require the header `Authorization: Bearer <password>`. The provided `index.html` handles all of this, so participants never touch the API directly.

---

## 2. Prerequisites

- A recent stable **Rust toolchain**. `main.rs` uses `Duration::from_hours`, which needs a fairly new compiler (1.91 or later). Run `rustup update` if the build complains.
- The project files (`Cargo.toml`, `src/`, etc.).
- A machine that participants can reach over the network (see section 7).

---

## 3. Setting up the `.env` file

Create a file named `.env` in the project root (next to `Cargo.toml`). The server loads it automatically on startup.

```env
SERVER_HOST=0.0.0.0
SERVER_PORT=3000
JWT_SECRET=replace-this-with-a-long-random-string
```

All three variables are **required**. The server exits with an error if any is missing.

| Variable | Meaning |
|----------|---------|
| `SERVER_HOST` | The IP address to listen on. Use `0.0.0.0` to accept connections from other machines, or `127.0.0.1` for local testing only. It must be an **IP address**, not a hostname, because it is parsed together with the port as a socket address. |
| `SERVER_PORT` | Port number (0 to 65535). The frontend assumes `3000` if the user leaves the port blank, so `3000` is the most convenient choice. |
| `JWT_SECRET` | The secret used to sign and verify passwords. Use a long random value (see below). |

Generate a good secret with either of these:

```bash
openssl rand -hex 32
```

```bash
python3 -c "import secrets; print(secrets.token_hex(32))"
```

**Important notes on `JWT_SECRET`:**

- Keep it private, and do not commit `.env` to git (add it to `.gitignore`).
- Passwords are only valid for the secret they were signed with. If you change the secret, **every password issued so far stops working**, and you must generate and send new ones.
- Password generation and the server must use the **same** secret.

## 4. Generating passwords

Passwords are generated by running the same program with two arguments, instead of starting the server.

### Step 1: Make the participant list

Create a plain text file with one participant per line. Only the **first word** on each line is used, and it becomes the email address. Anything after it is ignored.

`students.txt`:

```
alice@example.com
bob@example.com
carol@example.com  Carol Smith
```

### Step 2: Run the generator

```bash
cargo run --release -- students.txt passwords.csv
```

Or, if you have already built the binary:

```bash
./target/release/rcx students.txt passwords.csv
```

- The first argument is the input list, and the second is the output CSV. **Both are required.** Passing only one argument causes a crash.
- The `.env` file must be present, because the same configuration is loaded.
- If a password cannot be created for a line, the program prints a message and continues with the next one.

### Step 3: Check the output

`passwords.csv` has two columns:

```
mail_id,Password
alice@example.com,eyJ0eXAiOiJKV1QiLCJhbGciOi...
bob@example.com,eyJ0eXAiOiJKV1QiLCJhbGciOi...
```

The "password" is a long token. It is meant to be copied and pasted, not typed.

### Timing: passwords last 3 hours

The expiry is counted from the moment you run the generator, **not** from when the participant first uses it. So:

1. Generate the CSV shortly before the session starts.
2. Send the emails.
3. If the session runs long or people are late, generate a fresh CSV and send new passwords.

Older passwords are not revoked when you generate new ones. They simply keep working until they expire. The only way to invalidate everything immediately is to change `JWT_SECRET` and restart the server.

## 5. Sending the passwords

1. Open `passwords.csv`.
2. Email **each person their own row only**, ideally together with `UserInstructions.md` and `index.html`, plus the server **IP address and port**.
3. A mail merge works well for this: the `mail_id` column is the recipient and `Password` is the merge field.

Things to include in the email:

- The server IP (or URL) and port
- Their personal password
- The session time, and the fact that the password expires 3 hours after it was issued
- `index.html` and `UserInstructions.md` as attachments

**Do not send the whole CSV to everyone.** Each password identifies one person. It is also what the rate limiter uses to tell users apart, so shared passwords share one rate limit.

---

## 6. Starting the server

```bash
cargo run --release
```

With no arguments, the server starts. You should see a log line like:

```
listening on 0.0.0.0:3000
```

To stop it, press **Ctrl+C**. The server finishes in-flight requests before exiting. It also handles `SIGTERM` on Linux and macOS.

### Logging

Logging defaults to `rcx=info,tower_http=info`. Override it with the `RUST_LOG` environment variable, for example:

```bash
RUST_LOG=rcx=debug,tower_http=debug cargo run --release
```

Every minute the server logs the size of its rate-limit storage and cleans out old entries.

## 7. Making it reachable

- **Same network / LAN:** set `SERVER_HOST=0.0.0.0`, find the machine's IP, and give participants that IP and the port.
- **Firewall:** allow incoming TCP connections on `SERVER_PORT`.
- **Over the internet:** the server speaks plain HTTP, so passwords and inputs travel unencrypted. For anything beyond a trusted network, put it behind an HTTPS reverse proxy or tunnel (for example a Cloudflare tunnel). `index.html` supports this: if a participant pastes an `https://...` address into the host field, it uses HTTPS and does not assume port 3000.
- **Browser caveat:** if `index.html` is opened from an `https://` page, the browser will block requests to a plain `http://` server (mixed content). Either open the file locally or serve everything over HTTPS.
- CORS is fully open (any origin, any method, any header), so `index.html` works from anywhere.

## 8. Options and settings at a glance

| What | Where | Default |
|------|-------|---------|
| Listen address | `SERVER_HOST` in `.env` | none (required) |
| Port | `SERVER_PORT` in `.env` | none (required) |
| Signing secret | `JWT_SECRET` in `.env` | none (required) |
| Log level | `RUST_LOG` environment variable | `rcx=info,tower_http=info` |
| Password lifetime | `Duration::from_hours(3)` in `main.rs` | 3 hours |
| Rate limit | `.per_second(2)` and `.burst_size(5)` in `server.rs` | about 2 requests per second per user, bursts of 5 |
| Questions | `QUESTIONS` array in `questions.rs` | 12 questions |

The password lifetime and rate limit are compiled into the program, so changing them means editing the source and rebuilding. Participants who exceed the rate limit get an HTTP 429 error and can retry after a moment.

---

## 9. What participants see for bad input

- Input that breaks a question's constraints (wrong format, out-of-range values, extra tokens) still returns a normal response, with output such as `invalid input: n must be between 1 and 100000`.
- An invalid or expired password returns HTTP 401, and the page shows "invalid key".
- A question number that does not exist returns HTTP 404.

## 10. Troubleshooting

| Problem | Likely cause and fix |
|---------|----------------------|
| `SERVER_HOST environment variable is not set` (or similar) | `.env` is missing or not in the directory you run the command from. All three variables are required. |
| `Invalid SERVER_HOST and PORT combination` | `SERVER_HOST` must be an IP address like `0.0.0.0`, not a hostname. |
| `failed to bind server address` | The port is already in use, or you lack permission to use it. Pick another port. |
| Crash right after running with one argument | The generator needs both the input file and output file names. |
| Everyone gets "invalid key" | `JWT_SECRET` changed after the passwords were made, or the passwords expired. Regenerate and resend. |
| One person gets "invalid key" | Their password was copied incompletely (it is long), or it expired. |
| Participants cannot connect | Wrong IP or port, firewall blocking the port, or `SERVER_HOST` set to `127.0.0.1`. |
| Page loads but requests fail from an `https://` site | Mixed content blocking. See section 7. |
| HTTP 429 errors | The user is sending requests too quickly. Ask them to slow down. |
| Build fails on `Duration::from_hours` | Your Rust version is too old. Run `rustup update`. |
